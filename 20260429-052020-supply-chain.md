### GitHub Actions token permissions

The default `GITHUB_TOKEN` is broadly scoped unless the workflow narrows it. None of the three workflows declares a top-level `permissions:` block, and `release-dashboard.yml` declares no `permissions:` block at any level — meaning the entire job inherits whatever the repo's default token permission is.

- `.github/workflows/build-extension-catalog.yml:1` — missing top-level `permissions:`. Set `permissions: read-all` at the workflow level so jobs inherit read-only by default.
- `.github/workflows/build-extension-catalog.yml:17` — `actions: write` (sensitive). Required for the reusable workflow's caching/artifact step; keep, but only after the workflow-level read-all default is in place.

- `.github/workflows/build-extension-charts.yml:1` — missing top-level `permissions:`. Add `permissions: read-all`.
- `.github/workflows/build-extension-charts.yml:17` — `actions: write` (sensitive).
- `.github/workflows/build-extension-charts.yml:18` — `contents: write` (sensitive). Used for the `gh-pages` push; keep, but verify it is still required by the upstream reusable workflow at SHA `9eb70a7`.
- `.github/workflows/build-extension-charts.yml:19` — `deployments: write` (sensitive).
- `.github/workflows/build-extension-charts.yml:20` — `pages: write` (sensitive).

## Retro: dependency types not explicitly covered

### R1. yarnrc-format ↔ packageManager mismatch is invisible to the inventory

**What was seen.** `package.json:8` pins `packageManager: yarn@1.22.21+...` (Yarn 1, "yarn-classic"). `.yarnrc.yml` exists at the repo root with `nodeLinker: node-modules` and `pnpMode: false` — both of which are Yarn Berry (v2+) settings. Yarn 1 reads `.yarnrc` (no extension) and ignores `.yarnrc.yml` entirely, so the file is dead config in this repo.

**Why current rules missed it.** `inventory.py` parses `.yarnrc.yml` regardless of which Yarn major version the repo uses, then reports `enable_scripts: true` as a security-relevant signal. For yarn-classic that report is misleading: the YAML file is not consulted by the package manager, and the relevant lifecycle-script setting for Yarn 1 lives elsewhere (`yarn install --ignore-scripts` at the call site, or an `.yarnrc` keyword). Phase 2 has no rule to cross-check `lockfile_kind: yarn-classic` against the presence of a `.yarnrc.yml`.

**Proposed change.** In `inventory.py`'s Node detector, when `lockfile_kind == "yarn-classic"`, set `yarnrc.applies = False` (or null out `enable_scripts`) and add a `meta.warnings` entry like `".yarnrc.yml present but yarn-classic ignores it"`. Phase 2 should treat that warning as advisory only, not as an open issue.

### R2. Corepack `packageManager` SHA is a real pinning signal

**What was seen.** `package.json:8` carries `"packageManager": "yarn@1.22.21+sha1.1959a18351b811cdeedbd484a8f86c3cc3bbaf72"`. When corepack is enabled (the default on Node 20+), this SHA-1 is verified against the downloaded yarn tarball before it executes — i.e. the package manager binary is itself hash-pinned.

**Why current rules missed it.** Phase 1 enumerates lockfiles and Phase 2 verifies `integrity` lines, but the corepack `packageManager` field is invisible to both. A repo that pins yarn / npm / pnpm via this field is more strongly pinned than one that does not, and Phase 3 currently has no way to surface that.

**Proposed change.** Extend the Node detector in `inventory.py` to record `package_manager: { spec, version, hash_algo, hash }` per `package.json`. Add a Phase 2 sub-bullet that recognises a `packageManager` value matching `/(yarn|npm|pnpm)@[^+]+\+(sha1|sha224|sha256|sha384|sha512)\.[0-9a-f]+/` as a positive pinning signal, and flag a `packageManager` value without the `+<algo>.<hex>` suffix as an advisory open issue (corepack will fall back to "trust whatever it downloads").

### R3. CI build script lacks a verification step for the artifacts it produces — but this is a packaging concern, not a supply-chain one

**What was seen.** `.github/workflows/scripts/build-dashboard.sh:37` runs `sha512sum $RELEASE_LOCATION.tar.gz > ...sha512sum` and `release-dashboard.yml:58` uploads both files via `gh release upload`. The `.sha512sum` file is published alongside the tarball, but consumers who download both from the same GitHub release host get no out-of-band integrity guarantee — an attacker who could overwrite the release could overwrite both files.

**Why current rules missed it.** This is downstream-distribution integrity, not the upstream-dependency direction the skill scans. The skill explicitly checks "we verify what we pull in", not "we publish in a way our consumers can verify". So Phase 2 not flagging this is correct.

**Proposed change.** None to the skill itself — but the report should mention to Jan that adding cosign/sigstore signing of the release tarball, or publishing the digest to a separate channel (e.g. a signed GitHub release notes block, or a sigstore transparency log entry), would close the loop for downstream consumers. Track in the retro for visibility; keep out of "Open issues" since it is genuinely out of the skill's scope.
